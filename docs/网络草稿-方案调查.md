# 让 AI 画图的方案调查（网络草稿基础能力）

> 问题：有什么轻量的 skill 或开源项目，专门让 AI 画思维导图/关系图？
> 结论先给：**没有"标准答案"，但有一条清晰的光谱；我们现在的设计正好在光谱的正确位置。**

## 1 三条路线的分野

所有"让 AI 画图"的方案，都必须在**谁来布局**上做选择。

| 路线 | 代表 | AI 输出什么 | 谁算坐标 | 需要什么 |
|---|---|---|---|---|
| **A. 文本语法** | Mermaid、Markmap、Graphviz DOT、PlantUML | 带缩进/箭头的文本 | 引擎（ELK / dagre / dot） | **渲染运行时**（JS 或二进制） |
| **B. 坐标 JSON** | JSON Canvas、Excalidraw、tldraw | 节点 + 边 + **绝对 x/y/宽高** | **AI 自己** | 纯 JSON，零依赖 |
| **C. 语义结构 + 代码布局** | 本项目的 network 草稿 | 节点 + 边 + `layer` | **我们算** | 纯 JSON，零依赖 |

### A 路线：引擎布局，AI 只写文本

**Mermaid mindmap**（[语法](https://mermaid.js.org/syntax/mindmap.html)）最轻——缩进即层级：

```
mindmap
    Root
        A
            B
            C
```

- 支持 6 种节点形状（square / rounded / circle / bang / cloud / hexagon）
- `layout: tidy-tree` 可选布局；v12.2 起支持按深度着色
- ⚠ 官方标注 **experimental**，图标语法会变
- ⚠ 要跑一个 mermaid 运行时（几百 KB JS，还要 `mermaid.initialize`）

**Mermaid flowchart**（[语法](https://mermaid.js.org/syntax/flowchart.html)）：30+ 形状、边可带 id/文本/虚线/粗线，v12 起默认用 **ELK** 布局。能力最强，也最重。

**Markmap**（[markmap.js.org](https://markmap.js.org/)）：**Markdown → 思维导图**。因为输入就是 Markdown，AI 零学习成本，幻觉率最低。但仍要 markmap 运行时。

### B 路线：AI 给坐标

**JSON Canvas**（[规范 v1.0](https://jsoncanvas.org/spec/1.0/)，Obsidian 主导，2024-03）——这是目前最接近"AI 友好的图结构"的开放标准：

```json
{
  "nodes": [
    {"id": "a", "type": "text", "text": "根", "x": 0, "y": 0, "width": 200, "height": 60}
  ],
  "edges": [
    {"id": "e1", "fromNode": "a", "toNode": "b",
     "fromSide": "right", "toSide": "left", "toEnd": "arrow", "label": "引用"}
  ]
}
```

- 节点 4 类：`text` / `file` / `link` / `group`
- 边的可选位：`fromSide` / `toSide`（top/right/bottom/left）、`fromEnd` / `toEnd`（none/arrow）、`label`、`color`
- 6 个预设颜色（`"1"`~`"6"`），具体色值**故意不定义**，交给应用

**Excalidraw**：同样是坐标 JSON，额外有手绘风格。有一个[官方 MCP](https://github.com/excalidraw/excalidraw-mcp)（聊天里出图），和一个社区版 [`mcp_excalidraw`](https://github.com/yctimlin/mcp_excalidraw)（26 个工具的工作台）。

### C 路线：我们现在的做法

AI 只给 `layer`（负=上游、0=本体、正=下游），**坐标由渲染器算**。语义负担给 AI，几何负担给代码。

## 2 三条路线的真实代价

| | A 文本语法 | B 坐标 JSON | C 语义 + 代码布局 |
|---|---|---|---|
| 引入依赖 | **要一个渲染引擎** | 无 | 无 |
| 我们能不能直接渲染 | 不能（Jinja 出不了 SVG） | 能（自己画 SVG） | 能 |
| AI 幻觉风险 | 语法错（缩进/引号/`end` 关键字） | **布局错**（重叠、跑出画布） | 语义错（层级判断错） |
| AI 修改成本 | 重写整段文本 | 改一个坐标 | 改一个 layer |
| 大图（50+ 节点） | 引擎帮忙 | **AI 几乎不可能排好** | 代码排 |
| 与"草稿=数据"一致 | ❌ 草稿里存的是代码 | ✅ | ✅ |

**关键判断**：B 路线看似"标准"，但把布局负担压给 AI 是错的——AI 不擅长精确的二维排布，50 个节点必然重叠。Excalidraw 那套之所以可行，是因为它有**截图回环**（见下）让人/模型反复修。

## 3 最有价值的一个发现：`describe` + `screenshot` 回环

[`mcp_excalidraw`](https://github.com/yctimlin/mcp_excalidraw) 把"AI 画图"的真正难点说清楚了（原文）：

> the agent can query, screenshot, and update individual elements, **it iterates until labels fit, nothing overlaps, and arrows route cleanly**
>
> **Draw → look → adjust → look again**, element by element

它给了两个"让 AI 看见自己画了什么"的工具：

- **`describe_scene`**：结构化文本回读（id、位置、标签、连接）——**不需要多模态**
- **`get_canvas_screenshot`**：渲染成 PNG——需要能看图的模型

还有一件小事很聪明：**`read_diagram_guide`** —— 把"怎么画图"的指南做成一个工具，**按需加载**，而不是塞进 system prompt 常驻。

它的 26 个工具分七组（Element CRUD / Layout / Scene Awareness / File I/O / State / Viewport / Design Guide），其中 **Scene Awareness + Design Guide 是别人都没做的**。

## 4 另一个可抄的点：渲染失败要能教学

[`mcp-mermaid`](https://github.com/hustcc/mcp-mermaid) 的 README 明说它在做：

> `with validation for Mermaid` to facilitate the model's **multi-round output of correct syntax**

即：AI 写的图渲染不出来 → 返回结构化错误 → 模型改一版再试。这和我们对 `write_draft` 的思路一致（`bad_draft` 报原因），但**我们只校验了引用合法性（在不在库、边端点存在否），没校验"画出来会不会难看"**。

## 5 对我们 network 草稿的具体建议

### 5.1 保持 C 路线，不要为了"对齐标准"改用坐标

JSON Canvas 的坐标是给**人类拖拽**用的，不是给 AI 生成的。我们如果照搬，等于把最容易出错的部分交给 AI。

但可以从它那里**借边语义**——这是我们目前最薄的地方（现在边只有 `kind` + `note`）：

| JSON Canvas 字段 | 我们要不要 | 理由 |
|---|---|---|
| `label` | ✅ 要 | 边上的文字（"引用"、"扩展到"、"同一作者"），比 `kind` 更能表达意图 |
| `fromEnd` / `toEnd`（none/arrow） | ✅ 要 | 有些关系无方向（共引相似），画箭头是误导 |
| `fromSide` / `toSide` | ❌ 不要 | 这是布局细节，该由渲染器决定，AI 猜不准 |
| `color`（1~6 预设） | ✅ 要 | 6 个语义色：主线/上游/下游/旁支/存疑/分组 |

### 5.2 加一个 `read_draft` 的结构化回读（`describe`）

我们现在 `read_draft` 返回的是原始 payload + 卡。缺的是**"这图画出来长什么样"**的读数：

```
节点 12 个，边 15 条
层级：-2(2) -1(4) 0(3) +1(3)
孤立节点 1 个：2610.xxxx（没有任何边）
单层节点 8 个超过 6 个，渲染会很高
标题被截断的节点 2 个（超过 26 字）
```

**这才是 AI 能自我修正的东西**，而且纯文本、零多模态。

### 5.3 渲染器的三个"难看"检查（写进 `write_draft` 的体检）

现在 network 草稿的 `checkup` 只有 `no_card` / `recently_shown` / `top_share`（后两个是线性页的）。网络草稿该有自己的三项：

| 检查 | 为什么 |
|---|---|
| **孤立节点**（没有边） | 图上飘着一个点，说不清它为什么在 |
| **单层过宽**（某层 > N 个） | 我们的布局是"层=列、层内=行"，一层 20 个会把画布拉成面条 |
| **层级断裂**（连续层号之间跳空） | 说明 `layer` 写错了，画出来中间一列空白 |

**只报不拦**，和线性页一致。

### 5.4 明确不做的

| 不做 | 理由 |
|---|---|
| 引入 Mermaid / Markmap / Graphviz 运行时 | 违背"轻量"；Jinja + 手写 SVG 已经够画"层列图" |
| 让 AI 给绝对坐标 | 它在 50 节点时会重叠，且改一个节点要重算一片 |
| 截图回环 | 我们不需要"看"，因为渲染是确定性的（同一个 payload 永远同一张图）；结构化回读足够 |
| JSON Canvas 兼容导出 | 现在没有第二消费者；真需要时加一个 `export_draft(format="jsoncanvas")` 即可（结构几乎一一对应） |

## 6 如果将来要"更自由的图"

C 路线的天花板是"分层列图"。真要 AI 画自由布局（架构图、概念图），有两条备选：

1. **局部自由**：给节点加 `col` / `row` 覆盖（AI 只在对层布局不满意时才给，绝大多数情况不用）
2. **JSON Canvas 导出**：草稿本身仍是 C 路线，导出成 `.canvas` 让 Obsidian/Excalidraw 打开继续手调 —— **人改图，AI 画结构**，各干各的强项
