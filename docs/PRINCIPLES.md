# PaperPilot · 项目原则与设计哲学（项目宪法）

> 版本：v1.2 · 2026-09-25 立（v1.2 增补"手脚先行·与 AI 接入解耦"；v1.1 增补"人机共享工作台"）
> 地位：**本文是全项目的"基调文档 / 宪法"，层级高于 [`SPEC.md`](SPEC.md) 与 [`DESIGN.md`](DESIGN.md)。**
> 文档三层：本文（为什么 / 信什么）→ [`SPEC.md`](SPEC.md)（具体要实现什么）→ [`DESIGN.md`](DESIGN.md)（怎么实现）。
> 任何未来决策若与本文冲突，**以本文为准**，或必须先显式修订本文并在 §10 记录理由。
> 立此文档的目的：项目长大后不偏离初心——**防止以后忘了我们到底想要一个什么东西。**

## 1. 北极星（一句话定位）

> **PaperPilot 不是"一个带 AI 功能的文献软件"，而是"一个有手的 AI 研究助理"。**

你用自然语言跟它对话，它借一组**固化工具**替你：每天早上把 arXiv 关注领域的新论文筛完、读完、写成日报；持续维护你的**学术品味画像**；你点开感兴趣的，它替你下载归档、深度精读。

**核心体验 = 人机共享的 Web 工作台。** 主界面是本地 Web：人在上面直接操作，AI 也在上面操作、让界面随内部状态实时变化——**内部状态的写权由人和 AI 共同拥有**。对话是人指挥 AI 的主通道，Web 是这份共享状态的呈现与协作面。（详见信条 8）

> ⚠️ 初心校准：**AI 读明白、搜到，都还不够。** 本项目的价值最终落在"**人**能读到文献、获取到信息"，因此**人机交互与可视化是一等公民**，不是附属品。

## 2. 九条核心信条（The Creed）

这九条是项目的"基调"。做任何取舍、加任何功能前，先过一遍这里。

**信条 1 · 对话驱动 AI（Conversation drives the AI）**
人指挥 AI 的主通道是自然语言对话。能力不以"按钮"暴露给 AI，而以"AI 能调用的工具"暴露；用户表达意图，AI 负责理解、编排、执行、复述结果。（对话与 Web 主界面如何共存见信条 8）

**信条 2 · AI 管判断，工具管重活（LLM reasons, tools execute）**
LLM 是极强的**推理器/编排器**，但同时是又贵、又慢、又不精确的**执行器**。凡"步骤固定、数据量大、需精确可复现、高频重复"的活，一律固化成确定性工具；凡"意图模糊、需判断、需综合编排"的活，才交给 AI。（详见 §3）
**终极形态**：文献调研全流程按此二分——**能固化的都固化成程序，不好固化的都交给 AI**；理想终态是 **AI 能据自身使用体验反过来提议改进**工具/画像/流程（但改进须人确认，承信条 4；落地见 [`SPEC.md`](SPEC.md) §3.4）。

**信条 3 · Token 与内存是预算，不是免费的（Resource is a budget）**
**头号浪费 = 让 AI 直面海量原始数据。** 用漏斗式分层过滤、持久化缓存、浓缩结构化返回、上下文滚动摘要，把 LLM 调用压到"最小必要集"。（详见 §5）

**信条 4 · 关键动作要确认，一切写入可追溯可回滚（Confirm writes; traceable & reversible）**
只读工具 AI 自由调；写入类动作（改画像、下载、删除）**先提议、经用户确认再执行**，且带 `actor/reason` 落入 append-only 事件总线，可 `undo`。（详见 §6）

**信条 5 · AI 是奢侈品，不是必需品（Graceful degradation）**
AI 不可用/未配置时，系统必须靠"规则筛选 + 抽取式摘要"兜底，**业务流程一律走完**，页面标注降级原因。任何时候都不能因为"AI 挂了"而交不出日报。

**信条 6 · 不常驻，用完即走（Pulse, don't daemon）**
内存占用应是脉冲式的。手动（或定时兜底）触发 → 抓取分析出日报 → 能退就退；只有用户要看日报/对话时才起轻量本地服务。不为"7×24 挂着"付常驻成本。

**信条 7 · 画像是活的，且要防信息茧房（Living profile, guard the bubble）**
兴趣画像靠"种子 + 行为反馈 + 对话维护"持续进化；但自我强化会把你困在历史偏好里，日报须保留**探索配额**（画像之外但近期重要/引用飙升的少量论文）。

**信条 8 · 人机共享的工作台，可视化是一等公民（Shared human-AI canvas; visualization is first-class）**
主界面是本地 **Web**。它不是"人操作、AI 只能读"的传统软件，而是**人和 AI 共同操作同一份内部状态**的工作台：
- **写权共有**：内部状态的写权由人和 AI 同时拥有；每次写入都带 `actor/reason`、可追溯可回滚（承信条 4）。
- **AI 的操作要"看得见"**：AI 改动状态后，界面应随之实时变化，让人看得到"AI 刚才做了什么"。
- **对 AI 友好的操作形式**：AI 操作界面/状态时，优先走结构化工具调用 / 语义指令，而非模拟人去点鼠标。
- **可视化不是附属品**：因为价值最终落在"人读到信息"，界面呈现与交互质量与后端能力同等重要。

**信条 9 · 手脚先行，与"大脑"解耦（Capabilities first, decoupled from AI wiring）**
先把"手脚"（能力/工具）长好，再谈"大脑"怎么接：
- **能力必须中性、自描述、适合外部调用**（Python API + CLI 等 protocol-agnostic 形式），**独立于任何具体 AI 接入协议**。
- **绝不让某一种 AI 衔接方向反过来绑架能力设计**（旧仓库的 MCP/DSH 方向即为前车之鉴，不予沿用）。
- "AI 如何接入"是以后的事；能力先能被人、被其他程序、被未来任意 harness 调用。
- 界面分工：**与 AI 交互/监视的界面（界面①）**由外部承担，**可视化界面（界面②）**——结果呈现 + 人可直接操作——是本项目交付重点（详见 §7、[`SPEC.md`](SPEC.md) §1）。

## 3. 工具设计准则（本项目最核心、也最难的部分）

> 方针：**借 AI 的智能实现高度自由度，用固化的复杂工具节省 token。**
> "具体提供哪些工具"不预先拍脑袋定死，而是被真实使用逐步"逼"出来。

### 3.1 判断"该不该固化成工具"的尺子

出现下列**任一信号**，就应固化成确定性工具，而不是让 AI 每次临场推理：

- **数据量大**：如"从每天上千篇 arXiv 里筛候选"。必须工具化——工具用规则+embedding 把 1000 篇压到 20 篇，再把这 20 篇交给 AI。**这一层就省掉 95%+ 的 token，是全系统最大的省钱杠杆。**
- **步骤固定、每次都一样**：抓取、去重、增量、按分类过滤。
- **需精确可复现**：下载文件、写库、改画像的某个字段。
- **高频重复**：每天都在做的动作。

**反过来，留给 AI 自由推理的**：意图理解、价值判断（"这篇值不值得读"）、长尾低频操作、把多个工具结果综合权衡的编排逻辑、以及一切自然语言生成。

### 3.2 两个决定 token 效率的工具设计铁律

1. **粗粒度、面向意图，不要细粒度、面向步骤。**
   工具太碎（取一行、拼一个字符串）会逼 AI 来回调用十几次，每次往返都是 token + 延迟。要做到"一次调用 = 一个有意义的完整结果"，例如 `抓取今日候选(过滤条件) → 直接返回 Top N 结构化列表`。

2. **返回值必须浓缩且结构化，绝不把原始数据甩回给 AI。**
   工具内部就要完成聚合、裁剪、截断，只返回 AI 决策所需的**最小信息**；大回程被截断时必须附带"截了多少 + 完整数据去哪看"。原始数据一旦进上下文就是白烧钱。

### 3.3 渐进式固化方法论（"慢慢来"怎么走）

1. **先做最小起步集**：覆盖当前最高频的动作即可（见 §3.4）。
2. **盯住"固化信号"**：当发现 AI 在对话里**反复用自然语言临时拼凑同一类操作**、或**每次都要把一大堆数据读进上下文再处理**——那就是下一个该固化成工具的明确信号。
3. **先粗后细**：先用一个粗工具顶上，等某个子步骤真成了瓶颈或高频，再单独拆出来固化。

工具集要**被真实使用逼出来**，而非预先堆砌——这是"不过度工程"的具体落地。

### 3.4 起步工具清单（按读/写分类，对应 §6 护栏）

**只读工具（AI 可自由调用，无需打扰用户）**
- 抓取并筛选今日 arXiv 候选 ← 最重要的省 token 工具
- 读取当前兴趣画像
- 检索本地论文库（全文 / 关键词）
- 相似论文检索
- 取某篇论文的全文 / 摘要（供精读）

**写入工具（AI 必须先提议、用户确认后才执行）**
- 更新兴趣画像（增删改关键词 / 作者 / 领域 / 权重）
- 下载并归档论文
- （未来的）删除 / 清空记录

**纯 AI 推理层（不固化，就是它的本职工作）**
- 把自然语言翻译成画像改动，并复述给用户确认
- 精读时的总结、方法拆解、翻译、答疑
- 生成日报里"为什么推荐给你"的理由
- 决定一句话背后要调哪些工具、什么顺序

## 4. 兴趣画像准则（The Living Profile）

**4.1 混合式来源**
- **冷启动**：用户手写种子——关键词、领域分类、关注的作者/机构、几篇"这就是我想要的"标杆论文。
- **持续学习**：用户行为即标注数据。点开/下载/收藏 = 正反馈，忽略/划掉 = 负反馈，定期回灌画像。
- **对话维护**：用户直接说"我最近在看 X""别给我推 Y 了"，AI 翻译成结构化画像更新。

**4.2 对话维护画像的四道关（最易翻车处，必须做对）**
1. **翻译 + 确认**：AI 不能默默改。要把用户的话翻译成具体动作再回述确认——"我理解你要：新增关键词『扩散模型/医学影像』权重中高；给『强化学习』降权。对吗？"用户确认后才落库。
2. **可审计**：用户随时能问"我画像现在长啥样"，AI 能完整复述。
3. **可解释**：每条推荐**必带理由**，且理由能追溯到画像的哪一条（"因为你上周关注 X，本篇命中关键词 Y"）。
4. **可回滚**：画像改动进事件总线，支持"刚才那个改动撤回"。

**4.3 防茧房**：日报保留探索配额（默认少量），避免画像自我强化把用户困死。

## 5. 资源纪律（内存 & Token）

### 5.1 内存：不常驻
- 脉冲式占用：触发 → 跑完 → 退出；用时才起本地 Web/对话服务（信条 6）。
- 数据落 SQLite，进程本身无状态、可随时重启。

### 5.2 Token：漏斗 + 缓存 + 浓缩 + 上下文管理
- **三层漏斗**：① 元数据/规则粗筛（免费）→ ② embedding 语义召回（便宜/可本地）→ ③ LLM 精读（贵，只对 Top N）。
- **持久化缓存与去重**：论文按 `arxiv_id` 去重，分析过的结果永久存库，绝不重复烧 token。
- **批处理**：多篇合并进一个 prompt 打分。
- **上下文管理**：对话历史滚动摘要，只把"画像 + 当前任务"塞进上下文，而非全部聊天记录。
- **步数上限**：单个任务限制 AI 的工具调用往返次数，防止绕圈烧钱。
- **记账观测**：每次 AI 调用记 `ai_calls`（用途/耗时/token/成败），可按天汇总"今日 AI 开销"。

## 6. 安全护栏与可信（Guardrails & Trust）

- **读自由 / 写确认**：只读工具随便调；写入类先提议、结构化列清改动、用户一句确认后再执行（信条 4）。
- **append-only 事件总线**：所有写入带 `actor`(ai/human/scheduler) + `reason`(为什么) + before/after，DB 触发器钉死"只增不改"；`undo` 按 before 快照回写；不可逆操作明确拒绝并说明原因，不静默。
- **AI 幻觉防线（★ 2026-09-29 起改为"分级取数"）**：结构化 schema 强校验，解析失败即降级；
  总结与回答**只允许基于"真正取到的材料"**（prompt 约束"不得用外部知识"），而材料**分两级**：
  - **① 摘要档**（默认、轻）：标题＋摘要＋已有卡片——覆盖日报打分、推荐流、快速判断；
  - **② 全文档**（精读）：**只在 arXiv 提供了 HTML 的论文上可用**（归档正文、分节取用、
    在原文上落批注）——覆盖陪读、答疑、深度总结。
  **分级不等于放松**：取哪一档由任务决定；**没取到就不许编**。两档都必须**原文并排可核对**
  （详情页/日报并排展示；批注锚点回链原句），AI 转述永不替代原文核对。
- **可教学错误**：错误返回带 `kind/hint/suggest`，让用户和 AI"第一次错就能改对"。

## 7. 边界与非目标（Non-Goals）

- **来源统一 arXiv**：可叠加外部质量信号（如 Semantic Scholar 的引用数/TLDR）用于排序，但**不换源、不做多源抓取**（本期）。
- **个人单机自用**：不做多人协作、不做分布式、不追求高并发。
- **不过度工程**：工具集、功能都按需生长（§3.3），拒绝预先堆砌用不上的复杂度。
- **不自建大模型/训练**：只消费外部 AI 能力；embedding 优先复用外部框架或本地小模型。
- **不做"AI 接入/衔接"本身，也不做与 AI 交互/监视的界面（界面①）**：本项目只交付"手脚（中性能力层）+ 可视化界面（界面②）"；AI 怎么接、对话界面长什么样，由外部承担（承信条 9）。

## 8. 决策优先级（当冲突时怎么排）

> **初心与用户体验 > 资源成本（token/内存）> 实现便利。**

- 宁可多写一个确定性工具，也不让 AI 反复临场拼凑同一件重活（信条 2/3）。
- 宁可多一次"确认"，也不让 AI 静默改用户的数据（信条 4）。
- 宁可功能少而精，也不堆砌用不上的花活（§7）。
- 任何偏离本文的决策，必须在 §10 记录"为什么值得破例"。

## 9. 与现有实现的对照（防止文档与现实脱节）

本文不是空中楼阁——现有代码里**已经暗合**了多条原则，也有几处**待对齐**。

**已体现（继续保持）**
| 原则 | 现有落地 |
| --- | --- |
| 信条 2/3 · 固化工具 + token 纪律 | `mcp_server.py` 的 18 个 MCP 工具 = "AI 的手"；`_gate` 体积闸 + "摘要默认/明细显式要" |
| 信条 4/6 · 写确认可回滚 | append-only `events` 表 + `actor/reason` + `undo` + `/activity` 只读页 |
| 信条 5 · AI 非必需品 | `heuristic`/`unified`/`off` 三档降级 + `ai_calls` 记账 |
| 信条 1 · 对话即操作（部分） | DSH 提供 AI 对话框，AI 经 MCP 驱动 prepare→submit→finalize 三段评审 |
| 幻觉防线 | 结构化 schema 强校验 + 详情页并排原文摘要 |

**待对齐（本次"定基调"后应有意识靠拢的方向）**
- **Web 要成为"人机共享工作台"（信条 8）**：现有 `/settings`、`/papers` 等仍是"人操作、AI 只读"的传统表单。方向是——人和 AI 都能写同一份状态，AI 的写入要实时可视化反映到界面，对话作为人指挥 AI 的通道与 Web 并存。具体界面清单见 [`SPEC.md`](SPEC.md)。
- **画像的"对话维护 + 确认 + 可解释"尚未成型**：现在 `topics` 以 `settings.yaml` 为唯一事实源、靠 Web/CLI CRUD 改。方向是叠加"自然语言 → 翻译 → 确认 → 落库 → 可回滚"的对话式画像维护（§4.2），并让每条推荐带可追溯理由。
- **运行形态与"纯手动触发"存在张力**：现有 APScheduler 每天 07:30 常驻调度，与信条 6"不常驻、手动优先"需要重新权衡（手动/对话触发为主，定时作兜底而非主轨）。
- **能力仍绑在 MCP server 上（信条 9）**：18 个工具目前是 MCP 薄壳。方向是抽出**中性能力层**（typed + 自描述 + 统一返回信封），对外给 Python API + CLI(`--json`)，MCP 降为其上的一个可选 adapter。落地见 [`SPEC.md`](SPEC.md) §4。
