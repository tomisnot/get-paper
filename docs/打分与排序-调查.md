# 打分与排序：调查与落地

> 触发：2026-10-24 出 10-19~10-24 报告时，`score_papers` 的 25 条结果 `why` 清一色
> 「分类 quant-ph（占该维 +33%）」，分数挤在 0.157~0.353，排序几乎等于按 id。
> 用户裁决：**机制别堆，两三项就行，不然找 bug 都难**。

## 0 落地了什么（2026-10-24）

只上了**两条**机制，其余全部押后：

| # | 机制 | 一句话 |
|---|---|---|
| M1 | **短语命中** | 拿画像里已有的 term 键去扫这篇的**标题+摘要**（纯代码、零 AI 成本）。单字键不参与；3 词及以上算满，2 词 0.7；命中标题 ×1.0、命中摘要 ×0.6 |
| M2 | **维度内除以最大值** | 命中头号兴趣即满分，不再被"这一维里键太多"摊薄（原来除以总和，实测把所有人压到 0.17） |

同轮还补了三件**反馈面**的事（不是打分，但同属"画像数据质量"）：

| 机制 | 为什么 |
|---|---|
| **泛词黑名单** `is_generic_term` | 单字键里 `model`/`light`/`quantum`/`array` 这类在所有论文里都出现的词，进画像只能给全库加同一个常数。`paper_features` 里过滤 + 重算一次清掉存量 |
| **主/副分类加权**（1.0 / 0.6）、**作者 0.8** | 投稿主分类说明"属于哪个领域"，cross-list 只是"也沾一点"；作者是品味、噪声更大 |
| **出站链接过本站** | `outbound`(0.5) 与 `download`(1.0) 是权重最重的两个正向信号，直链 `arxiv.org` 会绕过系统把它们永久饿死 |

顺带修了一个**比打分更硬的 bug**：`score_papers(days=N, limit=K)` 原来只取
`repo.recent(days, limit=K*4)`——候选面被 `limit` 决定，`days=6, limit=10` 只看 40 篇、
全是最后一天的。改成候选面由时间窗决定（上限 2000），`limit` 只控制回几条。

### 实测（真实库 2166 篇 / 画像 97 条信号，窗口 10-19 起 449 篇）

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 词面维有贡献的论文 | 0%（无卡的论文词面恒 0） | 14%（65/449，只数多词短语） |
| 分数分布 | 0.157~0.353（挤在一起） | 中位 0.450、最高 1.000（有区分度） |
| 前 4 名 | 几乎按 id 排 | 全向重排（1.000）/ lattice gauge / Rydberg 阵列 ×2 |
| `why` | 清一色"分类 quant-ph" | 「短语『optical tweezer array』命中摘要（3 词，权重 5.7）」 |

注意那个 **97% → 14%** 的差别：把单字键（`quantum`、`arrays`）排除在短语命中之外，
覆盖率从 97% 掉到 14%，但**排序质量反而更好**——那 83% 是"全库都命中同一个词"的常数噪音。

## 1 诊断（改之前的现状）

当前打分（`scoring.score`）：

```
score = Σ_dim  α_dim × ( Σ_hit w / Σ_dim_all w )      α = 0.50 / 0.35 / 0.15
```

三个问题，按严重程度排：

### 1.1 分母是"整维权重和"，单篇贡献被摊薄成常数

分类维有 30 个键、总权重约 150；一篇 quant-ph 论文命中 1~3 个键（约 50 权重），
于是无论它命中的是"主分类"还是"顺手带的副分类"，贡献都落在 0.33 附近。
**这个数只说明"它属于哪个大类"，不说明"它讲的是不是你想看的"。**

### 1.2 大多数论文的词面维恒为 0

词面特征来自**卡**（`cards.terms`）。库 2166 篇、291 张卡 ⇒ 87% 的论文词面贡献为 0，
再乘 α=0.35 ⇒ 它们的分数上限天然低 35%。这不公平，也让"排序"退化成"有没有卡"。

### 1.3 三篇同分类论文得分几乎相同

差异只剩第三位小数，排序结果实质上由 `arxiv_id` 决定（代码里的 tie-break）。
**这就是"排序没帮上忙"的直接原因。**

## 2 业界怎么做的（查到的）

### 2.1 词频必须饱和（BM25 的 k1）

BM25 的 tf 项是 `f·(k1+1) / (f + k1·(1−b+b·|D|/d_avg))`：**k1 越小饱和越快**。
意义：一个词出现 3 次和出现 10 次，不该是 3 倍差距。[BM25 入门笔记](https://raw.githubusercontent.com/ethen8181/machine-learning/master/search/bm25_intro.ipynb)

对我们：**权重是累加的、没有上界**。现在的问题是分数普遍太低（0.17）而不是太高，
所以"饱和"不是第一优先级；但一旦把摘要词频也算进特征，必须立刻上 k1，否则一个词
出现 10 次就能压倒一切。

### 2.2 多路融合用排名，不用原始分（RRF）

搜索引擎融合多路召回时常用 `1/(k+rank)`（Reciprocal Rank Fusion）：只看名次不看分数，
**天然免疫"各路分数量纲不同"**。我们的 α 加权和恰恰被量纲坑了（分类维只有几十个键、
作者维几百个、词面维上千个 ⇒ 键多的维天然说话响）。

### 2.3 短视频：多级漏斗 + 重排多样性 + 探索配额

工业短视频推荐不是"一个模型打分排序"，而是
**召回（多路）→ 粗排 → 精排 → 重排（多样性/新鲜度/配额）**，重排阶段显式做
"同类降权、探索位、去重"。搜索结果的[全阶段多样化实验（WWW'24）](https://dl.acm.org/doi/abs/10.1145/3589334.3648144)
就是这套思路（我只读到标题与摘要级信息，未读全文）。

对我们的映射：
| 他们的环节 | 我们缺的 |
|---|---|
| 多路召回 | 只有"分类 + 卡 terms"，**没有标题/摘要短语** |
| 精排 | 有 `score`，但特征太薄 |
| 重排（多样性/配额） | **完全没有**：`score_papers` 是纯排序，同分类会霸榜 |
| 探索位 | 只在 `sample(mode="far")` 里有，排序里没有 |

## 3 用户三个问题的回答

### 3.1 太高的因素该不该饱和？

**该，但不是现在最缺的。** 我们的问题是分数普遍过低且无区分度。
饱和要用在"同一特征重复出现"的地方（词频），而不是用在"权重累加"上。
→ 先做归一化，等特征变厚（引入摘要短语/词频）时再上 k1。

### 3.2 某一维前几名直接抹平？

**不建议抹平成相等**——那会丢掉"第一比第十强很多"这个真实信号。
建议**压成亚线性**：维度内 `w' = sqrt(w)` 或 `log1p(w)`，再按名次给 `1/log(1+rank)` 的衰减。
效果：头部仍领先，但不会 10 倍碾压；偶然多几次点击不再垄断。

### 3.3 跨维度权重怎么定？

现在的 0.5/0.35/0.15 是拍的，而且**量纲不同直接相加是错的**。
两种改法（二选一）：
- **归一后加权**：每维先除以该维最大值（或改 rank），再按 α 加权；
- **RRF 融合**：`score = Σ α_d / (k + rank_d)`，与分数绝对值无关。

我倾向 RRF：少一个可调参数，对"某个维突然多了一堆键"免疫。
α 起点建议 **分类 0.45 / 词面 0.40 / 作者 0.15**——词面提权，因为它是"意图"，分类只是"领域"。

## 4 我认为比调参更重要的四件事

1. **给无卡论文也生成词面特征**（标题短语抽取，旧版 `title_terms` 做过）。
   这一条能把 87% 的论文从"词面恒 0"里救出来，收益比调任何参数都大。
2. **IDF**：现在键的权重只看点击次数，不看它在库里多稀有。
   `rydberg` 命中 300 篇、`atom transport` 命中 3 篇，前者该降权（BM25 的 IDF 项）。
3. **重排多样性**：`score_papers` 加 per-category / per-author 上限（旧版 feed 有
   `MAX_PER_CATEGORY`，可以搬）。否则一个热分类霸榜，用户看不到别的。
4. **探索位**：排序里留 1~2 个"低分但陌生"的位置，否则永远在舒适区。

## 5 施工顺序（P1 / P3 已做，其余待定）

| 阶段 | 内容 | 状态 |
|---|---|---|
| P1 | 无卡论文的标题/摘要短语特征 | ✅ 已做（M1） |
| P3 | 维度内归一化（除以最大值） | ✅ 已做（M2） |
| — | `score_papers` 候选面被 `limit` 掐窄 | ✅ 已修（bug） |
| P2 | IDF（键稀有度进权重） | 待定——现在靠"单词键不参与 + 短语长度打折"压泛词，够用 |
| P4 | 重排（分类/作者上限）+ 探索位 | 待定——只有上量才需要（一次 10~20 条还用不上） |
| P5 | 饱和（k1 / sqrt） | 押后——特征才刚变厚，现在上饱和是过早优化 |

**故意没做的**：RRF 融合。因为它会把"分类命中"变成纯名次，丢掉"命中头号分类 vs
命中边角分类"的差别；而 M2 的 max 归一已经解决了量纲问题，多一层融合只是多一个
调不动的旋钮。

## 6 明确不做

- **在线学习 / CTR 模型**：全库只有 97 条信号、4 个用户动作类型，纯过拟合。
- **embedding 语义检索**：本地没有算力预算，且当前瓶颈在特征不在模型。
- **多模型融合**：n=1 个用户，没有验证集，调不动。
